# LL-061 — Bills + posting

**Branch** `feat/ll-061-bills`

**Status** Backlog · **Origin** Sprint 6 plan (Accounts Payable). See
[SPRINT-6-PLAN.md](../SPRINT-6-PLAN.md). The structural mirror of LL-041/042 (invoices + posting).

> A **bill** is a vendor's invoice to us. DRAFT while edited; **finalize** posts it to the ledger
> and opens the payable. Corrections are by **void** (reversal), never edit (invariant 3).
>
> ### Schema
> A `bills` (+ `bill_lines`) pair mirroring invoices: `vendor_id` (composite-FK to a same-company
> vendor), `bill_date`, optional `due_date`, `status` (`DRAFT`/`OPEN`/`PAID`/`VOID`), lines with an
> expense `account_id` + amount, and derived `subtotal`/`tax_total`/`total` (**stored but always
> re-derived**, ADR-013 — never a balance). A gapless per-company `bill_number` on finalize. One
> migration.
>
> ### Posting (through `LedgerService`)
> `finalizeInvoice`'s mirror: recompute + assert totals, resolve the **A/P** system account, build
> **Dr Expense (per line account) / Cr A/P (`total`, vendor-tagged)**, allocate the number
> atomically, `postEntryCore` with source type **`EXPENSE`** (existing enum value), audit — all in
> one `getDbTx()` transaction. A line account may **not** be a system control account
> (`assertLineAccountsPostable`, ADR-016 item 1). `voidBill` reverses the entry and marks the bill
> VOID (guarded like invoices — see LL-062/063 for the adjustments guard).
>
> ### Rules
> `expense.view` / `expense.create` (reserved capabilities) for view / create+finalize; a new
> **`bill.void`** (LEDGER_WRITERS). Money is `string`/decimal.js; period resolved before the tx
> (ADR-007); one POSTED entry per bill (source-once index).
>
> ### Tests
> Finalize posts a balanced Dr Expense / Cr A/P (vendor-tagged) entry; double-finalize impossible;
> line-account-invalid rejected; void reverses; closed-period rejected; **GL-Txxx**: the A/P control
> moves by the bill total. Company scoping / no leak.
>
> ### Not in scope
> Bill payments (LL-062); vendor credits (LL-063); recurring bills; receipts/attachments.

**Accounting implications** A bill posts Dr Expense (by account) / Cr Accounts Payable, vendor-tagged,
through `LedgerService`; corrections are by void (reversal). A/P is now a system/control account, so
bill (and invoice) lines can no longer post to it (`LINE_ACCOUNT_INVALID`) — protecting the future
A/P aging⇔control reconciliation. No stored A/P balance (invariant 2).

**Security implications** `expense.*` / `bill.void`-gated, company-scoped; a cross-company id reads as
a genuine miss (no leak, §6); the vendor and every line account are re-validated in-company and the
composite FKs make a cross-tenant reference impossible.

**Decisions made that were not specified in the ticket** **Tax deferred** (your call) — no tax leg;
a bill's total is Σ its expense lines; input-tax is a later ADR-gated ticket. `expense.create`
authorizes both create and finalize (invoices' create/post are both ALL_WRITERS). Removed an unused
`DUPLICATE_BILL_NUMBER` error code (bill numbers are counter-allocated) during code review.

**Known limitations** No bill payments (LL-062), vendor credits (LL-063), aging/statement (LL-064),
or UI (LL-065). **`voidBill` has no reduction guard yet** — LL-062/063 MUST add
`BILL_HAS_PAYMENTS` / `BILL_HAS_ADJUSTMENTS` (the Gate-4 lesson) before a partially-reduced bill can
be voided, or the A/P tie would break. Bills/invoices are near-twins (shared-core refactor backlogged).

**Recommended follow-up** LL-062 (bill payments + the A/P control-account structural lock, generalizing
the 0018 trigger; and the voidBill reduction guard).
