# LL-052 — Ledger & audit hardening (Gate 2/3 follow-ups)


**Branch** `feat/ll-052-ledger-audit-hardening`

**Status** Backlog · **Origin** Sprint 5 plan · closes recorded low-severity items from
[GATE-2.md](../GATE-2.md) §7 and [GATE-3.md](../GATE-3.md) §7. See [SPRINT-5-PLAN.md](../SPRINT-5-PLAN.md).

> Defense-in-depth cleanup the gates surfaced — none currently exploitable, all worth making
> structural before more features post to the ledger. One logical migration (the trigger
> widening) plus app-layer redaction.
>
> ### Trigger widening (schema — plan mode)
> The balance/immutability triggers guard `status = 'POSTED'` only, and the immutability
> trigger's frozen-column list predates `idempotency_fingerprint` (migration 0008). Widen
> both to guard **`('POSTED','REVERSED')`** and to include `idempotency_fingerprint` in the
> frozen set (Gate 2 item 6). A REVERSED entry is history and must be as immutable as a POSTED
> one.
>
> ### Typed sum-overflow guard (schema or service)
> A balanced entry whose per-side SUM exceeds `NUMERIC(19,4)` is currently rejected at COMMIT
> with an opaque driver error (no partial state, but an ugly failure). Add a **typed
> magnitude guard** so it surfaces as a domain error before COMMIT (Gate 2 item 5).
>
> ### Audit redaction (app)
> The shared `redact()` helper has no pattern for `email` / `phone` / `billing_address` /
> `notes`, so customer PII persists verbatim in `audit_events` (Gate 3 item 3). Add those
> keys (or switch customer audit to a non-PII field diff). Do **not** loosen existing
> redaction — over-redaction elsewhere is the safe direction.
>
> ### Tests
> Raw-SQL `UPDATE` of a **REVERSED** entry / its lines is rejected by the trigger (service
> bypassed); the `idempotency_fingerprint` column is frozen post-insert; an over-`NUMERIC`
> entry fails with the typed error and leaves no rows; the redactor masks the new keys and a
> customer audit event no longer stores raw contact fields.
>
> ### Not in scope
> The manual-JE idempotency key and the void capability — those are LL-053.

## §11 report

**Ticket:** LL-052 — ledger & audit hardening (Gate 2 §7 items 5–6, Gate 3 §7 item 3).
**Branch:** `feat/ll-052-ledger-hardening`

**Scope note:** research narrowed it — the fingerprint freeze (Gate 2 item 6a) was already done by
migration 0011, and item 3 (customer-audit PII) was **ratified** by the product owner (no code
change). So this ticket = freeze REVERSED entries + the typed sum-overflow guard.

**Files changed:**
- Migration `0020_freeze_reversed_entries.sql` (new, function-replacement) + `_journal.json` + snapshot.
- `src/server/ledger/errors.ts` (`ENTRY_AMOUNT_OUT_OF_RANGE`); `src/server/ledger/index.ts` (`validateBalance` magnitude guard).
- `docs/DECISIONS.md` (ADR-020); `tests/integration/ledger-hardening.test.ts` (new).

**Migrations created:** `0020_freeze_reversed_entries.sql` — `CREATE OR REPLACE` of
`journal_entries_immutable` and `journal_lines_immutable` to freeze **REVERSED** entries and their
lines (previously guarded `POSTED` only). No table/column/data change; the existing triggers reference
the functions by name.

**DB constraints added:** none new (the two immutability triggers are widened in place).

**Tests added:** `ledger-hardening.test.ts` (5) — raw-SQL UPDATE/DELETE of a REVERSED entry and of its
lines rejected with `POSTED_ENTRY_IMMUTABLE` (service bypassed); the POSTED→REVERSED reversal still
succeeds and a DRAFT stays editable; a balanced over-`NUMERIC(19,4)` entry → `ENTRY_AMOUNT_OUT_OF_RANGE`;
an at-the-ceiling entry posts.

**Test results:** lint ✓ · typecheck ✓ · unit ✓ (175) · integration ✓ (hardening 5; full suite as the
gate) · build ✓. e2e n/a.

**Accounting implications:** invariant 3 (immutability) now covers the reversed original, not just the
posted state — a reversed entry's audit trail cannot be silently rewritten. Invariant 1 gains a typed
ceiling instead of an opaque COMMIT overflow.

**Security implications:** the REVERSED freeze is structural (holds with the app bypassed, proven by
raw SQL). Customer-audit PII ratified (ADR-020): access-controlled, not a §9 secret.

**Decisions made not specified in the ticket:** ADR-020 — REVERSED immutability, bounded entry totals,
and the customer-audit-PII ratification (item 3 → no code).

**Known limitations:** the magnitude guard is on the manual posting path (`validateBalance`); document
services derive bounded amounts (a shared assert across all paths is a possible later extension).

**Recommended follow-up:** LL-053 (void authorization + idempotent writes), then LL-054/055
(statements + reporting UI) and Gate 4.
