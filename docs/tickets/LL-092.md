# LL-092 — Lock the company row in postEntryCore (Gate 6 H3)

**Branch** `feat/ll-092-post-company-lock` · **Status** implemented · **Origin** Gate 6 data-integrity
HIGH-1 (= accounting LOW-5, data LOW-6). Design: ADR-039 amendment.

## Problem
`postEntryCore` read the company row (`status`, `isTemplate`) without a lock before `allocateEntryNumber`
took the counter lock. `setCompanyTemplate`, `updateCompanySettings` and `deleteCompany` decide under the
counter lock + a count of posted entries, so a posting that read the company first could land after they
committed: a template with history, or a post into an archived company.

## §11 — End-of-ticket report

**Ticket:** LL-092 — `postEntryCore` takes the company row `FOR KEY SHARE`.
**Files changed:** `src/server/ledger/index.ts` (one lock clause + rationale); `src/server/ledger/reversal.ts` (`reverseEntryCore` takes the same key-share read at its top, closing the archive-vs-reversal window); `tests/integration/company-template.test.ts`
(two deterministic lock-conflict cases); ADR-039 amendment; this ticket.
**Migrations created:** none. **DB constraints added:** none.
**Tests added:** (1) a real posting started while a designation holds the company row `FOR UPDATE` stays
blocked, then fails with `TEMPLATE_COMPANY` once the designation commits; (2) `setCompanyTemplate` started
while a transaction holds the row in key share stays blocked, then succeeds (nothing posted). Together they
prove the two operations serialise instead of both passing.
**Test results:** lint ✓ / typecheck ✓ / unit ✓ / build ✓ (`npm run ci`); integration on CI's ephemeral
branch (the local suite truncates the shared dev database).
**Accounting implications:** the "template has zero entries, always" and "archived company receives no
posting" claims are now lock-ordered facts. Accounting periods are calendar months
(`src/server/periods/index.ts`), so a fiscal-year-start change cannot re-derive a posting's period — the
reviewer's period-mismatch variant was not reachable; `SETTINGS_LOCKED` is likewise now race-free.
**Security implications:** none.
**Decisions made not specified in the ticket:** KEY SHARE (the weakest strength that conflicts with the
services' FOR UPDATE) rather than moving the read after the counter lock, so lock order stays company →
counter everywhere and the check keeps its place at the top of the core.
**Known limitations:** none known.
**Recommended follow-up:** none.
