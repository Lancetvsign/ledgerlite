# LL-056 — Configure the production deploy pipeline (credentials) or document the deploy story

**Branch** `chore/ll-056-deploy-skip-when-unconfigured`

**Status** Implemented (see §11) · **Origin** Gate 4 §7 item 5 (pre-existing, surfaced during the Sprint 5 acceptance review).

> The **"Production deploy"** GitHub Actions workflow (`Migrate, then promote`) fails at its
> **"Require credentials"** step on **every** commit — verified red back through Sprint 4
> (27538f2, 2fd5c85, a6b5cee, …), so it is **not a Sprint 5 regression**. The gating **CI**
> workflow (lint · types · unit · build · Integration · GL regression · E2E) is green on
> `main`; only the deploy job is red, because the production deploy secrets are not present in
> this repo, and the job fails fast by design when they are absent.
>
> Net: **production deploys have never run**. This is an operational/infra gap, out of scope
> for a code-acceptance gate, but it must be closed before go-live.
>
> ### Scope
> - Decide the deploy target and provision the required secrets (Vercel token / project +
>   Neon production `DATABASE_URL`, per the workflow's `Require credentials` step) in GitHub
>   Actions secrets — **never in source** (AGENTS §9). Do not read/write `.env.production`.
> - Confirm the **expand → migrate → contract** production migration flow (AGENTS §5) runs
>   under the advisory lock against the production branch only.
> - If a hosted production environment is intentionally deferred, **document that** and make
>   the deploy workflow a no-op or explicitly skipped rather than a hard failure, so `main`
>   stops showing a red deploy on every commit.
>
> ### Acceptance
> Either a green production deploy on `main`, or a documented, intentional skip — and the
> "Require credentials" hard-failure no longer fires on every commit.
>
> ### Not in scope
> Any application code change; the gating CI workflow (already green).

## §11 — End-of-ticket report

**Ticket:** LL-056 — configure the production deploy pipeline, or document the deploy story.
**Branch:** `chore/ll-056-deploy-skip-when-unconfigured`
**Chosen path:** the ticket's second acceptance path — **documented, intentional skip** — since no
hosted production environment is provisioned and the product owner confirmed deferral. The pipeline is
made **self-enabling**: adding the production secrets later turns the deploy on with no further edit.

**Files changed:**
- `.github/workflows/production-deploy.yml` — split into a `preflight` job that decides whether
  production is provisioned, keyed on the **production database URL**
  (`PRODUCTION_DATABASE_URL_UNPOOLED`, read as env since secrets are not allowed in `if:`): absent →
  `configured=false` (deploy **skips**, neutral, with a `::notice`); present → `configured=true` (full
  gated deploy runs). The existing `migrate-then-deploy` job is gated
  `if: needs.preflight.outputs.configured == 'true'` and otherwise unchanged, retaining its fail-closed
  `Require credentials` guard (Vercel creds + DB URL) immediately before touching production.
  **Correction (post-merge):** the first version keyed the skip on ALL FOUR secrets and hard-failed on
  a partial set. But the Vercel creds already exist for Preview/linkage (LL-006), so the repo's real
  state is 3/4 present — which that logic wrongly flagged as a misconfiguration, leaving `main` red (the
  very thing the ticket fixes). Corrected to key the skip on the production DB URL alone (the true
  "is production stood up?" signal); the in-job guard still fail-closes on the full set.
- `docs/DEPLOYMENT.md` — amended the "fail, don't skip" note to carve out the deploy as the one
  deliberate exception (a deploy is an action, not a correctness gate) and added a **"Production deploy
  status — deferred"** section with the ordered go-live runbook (Neon → Vercel → auth secrets → GitHub
  Actions secrets → manual gate → trigger).
- `docs/tickets/LL-056.md` — this report.

**Migrations created:** none.
**DB constraints added:** none.
**Tests added:** none — this is CI/deploy topology. No unit/integration test can assert GitHub Actions
job wiring; the proof is behavioural (below).
**Test results:** `npm run ci` unaffected (no app code). YAML validated (`js-yaml` parse; two jobs,
`preflight` → `migrate-then-deploy` with the skip gate). The behavioural proof is this PR's own
"Production deploy" run on merge to `main`: with no secrets set, `preflight` succeeds and
`migrate-then-deploy` shows **skipped** — `main` no longer carries a red deploy on every commit.

**Accounting / security implications:** none new. Secrets stay out of source (§9); production migrations
are still run only by the workflow, under the advisory lock on the direct endpoint, and Vercel promotes
only if they succeed. The skip cannot be mistaken for a successful deploy — nothing is promoted, so
production keeps running exactly what it already ran.

**Decisions made not specified in the ticket:** implemented the skip via a two-job preflight/gate
(cleanest way to get a *neutral* skip rather than a hard failure, since job-level `if:` cannot read
secrets directly); kept a redundant in-job credential guard as a fail-closed final check before the
production DB.

**Known limitations:** the end-to-end production deploy (a real gated migrate-then-promote, and that a
failed migration blocks promotion) remains **unverified** until real secrets and infra exist — by
design; this ticket closes the "red on every commit" and documents the go-live path, it does not stand
up production.

**Recommended follow-up:** none required. When go-live is wanted, follow the DEPLOYMENT.md runbook to
add the secrets; the deploy self-enables on the next push.
