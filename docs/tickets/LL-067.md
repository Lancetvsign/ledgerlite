# LL-067 — Submit-once idempotency for money-in / money-out documents

**Branch** `feat/ll-067-payment-idempotency` · **Status** Backlog · **Origin** Gate 5 (correctness
finding 2). Also the beta-roadmap "submit-once idempotency" item.

> `receivePayment` (A/R), `payBill`, and `issueVendorCredit` (A/P) mint a new document id per call
> and post through `postEntryCore(…, undefined)` — **no idempotency key**. The source-once index
> dedupes retries of the SAME document, but a client retry after a lost response creates a NEW
> document, so a *partial* payment/credit can post twice. Reconciliation still holds (subsidiary and
> control move together), which is exactly why it would go unnoticed — but cash is over-disbursed
> and two cheques exist. A retried *full* payment is caught (`BILL_NOT_OPEN` / `INVOICE_NOT_OPEN`);
> partials are not (invariant 6: "retries are idempotent").
>
> ### Approach
> Carry a client-supplied idempotency key through the payment / bill-payment / vendor-credit inputs
> to `postEntryCore` (the fingerprint machinery already exists — LL-032), so a retry with the same
> key returns the existing document rather than posting a second. The UI generates the key per form
> render (a hidden field), so a double-submit or a network retry is a no-op. Do A/R and A/P together
> — they share the pattern and the `postEntryCore` fingerprint path.
>
> ### Tests
> Concurrency test (real DB): N simultaneous submits of one keyed partial payment → exactly one
> posts; a resubmit with the same key returns the first document; a genuinely different payment with
> a fresh key posts normally. Extend `adv6-ap-concurrency.test.ts` and the A/R equivalent.
