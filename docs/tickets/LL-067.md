# LL-067 — Submit-once idempotency for money-in / money-out documents

**Branch** `feat/ll-067-payment-idempotency` · **Status** Backlog · **Origin** Gate 5 (correctness
finding 2). Also the beta-roadmap "submit-once idempotency" item.

> `receivePayment` (A/R), `payBill`, and `issueVendorCredit` (A/P) mint a new document id per call
> and post through `postEntryCore(…, undefined)` — **no idempotency key**. The source-once index
> dedupes retries of the SAME document, but a client retry after a lost response creates a NEW
> document, so a *partial* payment/credit can post twice. Reconciliation still holds (subsidiary and
> control move together), which is exactly why it would go unnoticed — but cash is over-disbursed
> and two cheques exist. A retried *full* payment is caught (`BILL_NOT_OPEN` / `INVOICE_NOT_OPEN`);
> partials are not (invariant 6: "retries are idempotent").
>
> ### Approach
> Carry a client-supplied idempotency key through the payment / bill-payment / vendor-credit inputs
> to `postEntryCore` (the fingerprint machinery already exists — LL-032), so a retry with the same
> key returns the existing document rather than posting a second. The UI generates the key per form
> render (a hidden field), so a double-submit or a network retry is a no-op. Do A/R and A/P together
> — they share the pattern and the `postEntryCore` fingerprint path.
>
> ### Tests
> Concurrency test (real DB): N simultaneous submits of one keyed partial payment → exactly one
> posts; a resubmit with the same key returns the first document; a genuinely different payment with
> a fresh key posts normally. Extend `adv6-ap-concurrency.test.ts` and the A/R equivalent.

## §11 — End-of-ticket report

**Ticket** LL-067 — Submit-once idempotency for money-in / money-out documents · **Branch**
`feat/ll-067-payment-idempotency`

**Files changed**
- `src/server/ledger/fingerprint.ts` — new `fingerprintRequest(material)` (canonicalises object keys,
  keeps array order); `fingerprintPosting` unchanged.
- `src/server/ledger/index.ts` — export `isIdempotencyViolation`; new `findIdempotentDocument` (returns the original doc for a key that already posted, or null)
  (find the prior entry by key, verify fingerprint, load the document its `source_id` points at);
  export `fingerprintRequest`.
- `src/server/{payments,bill-payments,vendor-credits}/index.ts` — `receivePayment`/`payBill`/
  `issueVendorCredit` accept an optional `idempotencyKey`; when present, fingerprint the request, post
  with key + fingerprint, and on a collision resolve to the ORIGINAL document. Keyless calls unchanged.
- `src/validation/{payment,bill-payment,vendor-credit}.ts` — `idempotencyKey: z.uuid().optional()`.
- `src/app/{payments,bill-payments}/{new/page,*-form,actions}.tsx` — the page mints
  `crypto.randomUUID()` per render, the form renders a hidden `idempotencyKey` field, the action
  forwards it.

**Migrations created** None — reuses the `journal_entries.idempotency_key` / `idempotency_fingerprint`
columns and partial unique index from LL-032.

**DB constraints added** None (existing `journal_entries_idempotency_unique` now covers documents too).

**Tests added**
- `adv6-ap-concurrency.test.ts` (A/P): 6 simultaneous same-key payments → ONE payment (all resolve to
  it), open balance not doubled; resubmit → same payment, a new key → a second; same key + different
  content → `IDEMPOTENCY_KEY_CONFLICT`; keyless still posts.
- `payments.test.ts` (A/R): the concurrent-same-key and resubmit / keyless cases for `receivePayment`.
- `tests/unit/ledger-fingerprint.test.ts`: `fingerprintRequest` determinism, key-order independence,
  array-order sensitivity, value sensitivity.

**Test results** lint ✅ · typecheck ✅ · unit ✅ **182** · build ✅. Integration (`adv6`, `payments`)
+ `test:gl` on CI's ephemeral branch — a local run truncates the dev DB.

**Accounting implications** A double-submit / network-retry of one payment or vendor credit is now a
no-op returning the original document, so cash cannot be over-disbursed (invariant 6). Reconciliation
is unaffected — the mechanism prevents the duplicate rather than compensating after it.

**Security implications** The key is a client request id, never money (Zod `uuid().optional()`); a key
reused for different content is refused (`IDEMPOTENCY_KEY_CONFLICT`), never silently merged, so a
crafted resubmit cannot make a payment resolve to an unrelated one. Company scoping unchanged.

**Decisions made that were not specified in the ticket** The approved plan said
`fingerprintPosting(ledgerInput, {includeSourceId:false})`; during implementation that proved
INSUFFICIENT — the derived posting does not capture which bills/invoices the applications targeted, so
two same-total payments to different targets under one key would falsely match. Corrected to a
`fingerprintRequest` over the request itself (ADR-026). (2) The key is resolved **before** the
service's state-dependent validation, not only in the post-time catch — otherwise a network retry of
a payment larger than the winner's remaining open balance would fail `OVERAPPLIED` instead of
returning the original (caught in self-review; `findIdempotentDocument` returns the doc-or-null and is
called in both places). ADR-026 records both.

**Known limitations** `issueCreditMemo` / `writeOffInvoice` (A/R reduction siblings) do not yet take a
key — a small extension of the shared helpers (noted follow-up). No UI for vendor credits, so its
service supports the key but nothing wires it yet.

**Recommended follow-up** LL-070 (integration-CI sharding — the recurring timeout tax) before
LL-068/069; then the credit-memo / write-off idempotency extension.
