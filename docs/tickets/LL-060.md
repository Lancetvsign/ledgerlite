# LL-060 — Vendors

**Branch** `feat/ll-060-vendors`

**Status** Backlog · **Origin** Sprint 6 plan (Accounts Payable). See
[SPRINT-6-PLAN.md](../SPRINT-6-PLAN.md). The structural mirror of LL-040 (customers) — the party a
**bill** owes.

> The vendor entity that bills and bill payments reference. A direct mirror of customers (LL-040):
> **no ledger effect**, no stored balance (invariant 2) — a vendor's A/P balance is derived from
> journal lines, later.
>
> ### Schema
> A `vendors` table: `id`, `company_id`, `name` (required), optional `vendor_number`, contact
> fields, `status` (`ACTIVE`/`INACTIVE` — deactivate, never delete, ADR-006), timestamps.
> Composite-FK tenancy: `UNIQUE (company_id, id)` — the hook the ledger's
> `journal_lines (company_id, vendor_id)` FK builds on, so a line can never reference another
> tenant's vendor. `UNIQUE (company_id, vendor_number)` and a `(company_id, name)` index.
> One migration.
>
> ### Service
> `createVendor` / `updateVendor` / `deactivateVendor` / `getVendor` / `listVendors`, company-scoped,
> mirroring the customer service. A cross-company / unknown id reads as a genuine miss (no leak, §6).
>
> ### Rules
> New capabilities **`vendor.view`** (EVERYONE) and **`vendor.manage`** (ALL_WRITERS); update the
> exhaustive `rbac.test.ts` matrix (known gotcha — run `npm run ci` before pushing). Money N/A here.
>
> ### Tests
> CRUD + deactivate; company scoping / no existence leak; the isolation descriptor for `vendors`;
> the rbac matrix.
>
> ### Not in scope
> Bills (LL-061); any A/P balance (derived, LL-064); vendor merge; 1099 fields.
