# LL-069 — Allow-list audit payloads for vendor & customer free-text (§9)

**Branch** `feat/ll-069-audit-field-allowlist` · **Status** Backlog · **Origin** Gate 5 (security
LOW-3). LOW; company-partitioned; parity issue across A/R and A/P.

> `createVendor`/`updateVendor`/`deactivateVendor` (and the identical customer service) audit the
> WHOLE row (`after: vendor` / `before: existing`). `redact()` runs, but its patterns don't cover
> free-text `notes`/`address`/`email`/`phone`, nor bank account / routing numbers. AGENTS §9 lists
> "bank credentials" among values that must never land in the audit log — so a user who types vendor
> remit-to banking details into `notes` persists them verbatim in `audit_events.after_json`.
>
> ### Approach
> Audit an explicit **field allow-list** (`name`, `vendorNumber`/`customerNumber`, `status`) instead
> of the whole record, for BOTH the vendor and customer services (parity). The audit event's purpose
> is "who changed what status/identity, when" — not a copy of every contact field. Alternatively,
> extend `redact()`'s key patterns to cover the free-text fields; the allow-list is safer (default
> deny). No schema change.
>
> ### Tests
> `audit.test.ts`: a vendor/customer created with a `notes` value containing a bank-account-shaped
> string produces an audit row whose `after_json` does NOT contain it.
