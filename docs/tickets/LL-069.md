# LL-069 — Allow-list audit payloads for vendor & customer free-text (§9)

**Branch** `feat/ll-069-audit-field-allowlist` · **Status** Implemented (see §11) · **Origin** Gate 5
(security LOW-3). LOW; company-partitioned; parity issue across A/R and A/P.

> `createVendor`/`updateVendor`/`deactivateVendor` (and the identical customer service) audit the
> WHOLE row (`after: vendor` / `before: existing`). `redact()` runs, but its patterns don't cover
> free-text `notes`/`address`/`email`/`phone`, nor bank account / routing numbers. AGENTS §9 lists
> "bank credentials" among values that must never land in the audit log — so a user who types vendor
> remit-to banking details into `notes` persists them verbatim in `audit_events.after_json`.
>
> ### Approach
> Audit an explicit **field allow-list** (`name`, `vendorNumber`/`customerNumber`, `status`) instead
> of the whole record, for BOTH the vendor and customer services (parity). The audit event's purpose
> is "who changed what status/identity, when" — not a copy of every contact field. Alternatively,
> extend `redact()`'s key patterns to cover the free-text fields; the allow-list is safer (default
> deny). No schema change.
>
> ### Tests
> `audit.test.ts`: a vendor/customer created with a `notes` value containing a bank-account-shaped
> string produces an audit row whose `after_json` does NOT contain it.

## §11 — End-of-ticket report

**Ticket:** LL-069 — allow-list audit payloads for vendor & customer free-text (§9).
**Branch:** `feat/ll-069-audit-field-allowlist`

**Files changed:**
- `src/server/vendors/index.ts` — added a default-deny `auditView(v)` projection returning
  `{ id, name, vendorNumber, status }`; `createVendor`/`updateVendor`/`deactivateVendor` now audit
  `auditView(...)` instead of the whole row (`after`, and `before`+`after` on update/deactivate).
- `src/server/customers/index.ts` — the mirror: `auditView(c)` → `{ id, name, customerNumber, status }`,
  applied to all three mutations (parity, A/R ⇔ A/P).
- `docs/DECISIONS.md` — ADR-028 (allow-list over extending `redact()`; the reasoning and trade-off).
- `tests/integration/audit.test.ts` — new describe block (below).
- `docs/tickets/LL-069.md` — this report.

**Migrations created:** none (no schema change).
**DB constraints added:** none.
**Tests added:**
- `audit.test.ts` "a vendor created with bank details in notes: notes never reach after_json" and its
  customer twin — each creates a party with a bank-account-shaped `notes` (plus email/phone/address),
  then asserts the sentinel and the other free-text contact fields are **absent** from `before_json`/
  `after_json` across CREATE, UPDATE (both before and after), and DEACTIVATE, while the allow-listed
  identity/status (`name`, number, `ACTIVE`/`INACTIVE`) **is** present. Proves both the leak is closed
  and the audit row stays useful.

**Test results:** lint ✓ / typecheck ✓ / unit ✓ / build ✓ (local `npm run ci`). The new audit tests
are DB-backed (integration) and run on the PR's CI Integration shards, not locally against the shared
dev branch (per contract).

**Accounting implications:** none — no ledger, posting path, or financial data touched.
**Security implications:** closes the §9 leak where a user could persist bank/remit-to details (typed
into `notes`/`address`) verbatim in `audit_events.after_json`. The audit trail still records who
changed a party's identity/status and when. `redact()` continues to run on top (defence in depth); the
allow-list is fail-safe (a new free-text field cannot leak unless deliberately added to `auditView`).
**Decisions made not specified in the ticket:** included `id` in the allow-list (non-sensitive entity
identity, aids reading `after_json` in isolation); recorded the allow-list-vs-extend-`redact()` choice
as ADR-028 for traceability (the ticket only suggested an ADR note in passing).
**Known limitations:** vendor/customer audit rows no longer capture contact-field diffs (a change to
`email` alone yields an identical-looking before/after) — accepted per ADR-028; field-level contact
history is not the audit trail's purpose and is exactly the leak. Other audited entities were out of
scope (they do not carry party free-text); a future central structured-redaction policy could fold
these two local projections in.

**Recommended follow-up:** none required. This was the last Gate 5 follow-up ticket.
