# LL-031 — LedgerService


**Branch** `feat/ll-031-ledger-service`

> Implement LL-031: `LedgerService`, the **only** approved mechanism for creating
> posted journal entries. No feature module will ever insert into `journal_entries` or
> `journal_lines` directly.
>
> ### Input
> ```
> companyId, actorUserId, transactionDate, postingDate, description,
> sourceType, sourceId, idempotencyKey,
> lines: [{ accountId, description, debit, credit, customerId?, vendorId? }]
> ```
> Money arrives as `string`, per ADR-004. Validate with Zod. **Reject a JavaScript
> `number` in a money field at the schema boundary** rather than coercing it — silent
> coercion is how float error enters an accounting system.
>
> ### Validation pipeline, in order, all before any write
> 1. **Authorization** — `requirePermission(actorUserId, companyId, 'journal.post')`.
> 2. **Company validation** — the company exists and is active.
> 3. **Account validation** — every referenced account exists, belongs to this company,
>    and is active. Inactive account → `INACTIVE_ACCOUNT`.
> 4. **Period validation** — `assertPeriodOpen(companyId, <date per ADR-002>)`.
>    Closed → `PERIOD_CLOSED`.
> 5. **Balance validation** — sum debits and sum credits with `decimal.js`. Require
>    exact equality at `NUMERIC(19,4)`. Never use `===`, never use an epsilon
>    comparison. Unequal → `UNBALANCED_JOURNAL_ENTRY`.
> 6. **Structural validation** — at least two lines; each line exactly one positive
>    amount; no negatives.
> 7. **Idempotency** — see LL-032.
>
> Every failure is a typed error with a stable machine-readable code. No partial
> database state may remain after any failure.
>
> ### Posting — atomicity is the requirement
>
> - Use **`dbTx`**, the Pool client. Not the HTTP client. Per ADR-001 the HTTP client
>   cannot do interactive transactions, and simulating one with sequential statements
>   plus compensating deletes is prohibited.
> - One `db.transaction()` covers: entry header insert, all line inserts, status set to
>   `POSTED`, `posted_at` set, and the audit event write. The audit event goes **inside**
>   the transaction — an audit record that survives a rolled-back posting describes
>   something that never happened.
> - Return the resulting journal entry with its lines.
>
> ### Tests
>
> Unit: every validation rule in isolation, each asserting the specific error code.
>
> Balance cases: 100.00/100.00 passes; 100.00/99.99 fails; multiple debit lines;
> multiple credit lines; four-decimal amounts that only balance at full precision
> (0.3333 + 0.3333 + 0.3334 = 1.0000); very large amounts near the `NUMERIC(19,4)`
> bound; amounts that a float would round incorrectly — include 0.1 + 0.2 = 0.3 and
> confirm it passes, which a float implementation fails.
>
> Period: open period; closed period; both boundary dates; a company whose fiscal year
> does not start in January; another company's period.
>
> **Atomicity — failure injection, required.** Inject a failure after the header insert
> and after the first line insert. Assert afterward that the database contains: no
> journal entry, no journal lines, no audit event. Do this against a real database, not
> a mock. If your injection technique cannot reach the state you need to test, say so
> explicitly rather than substituting a weaker test.
>
> **Constraint reliance is intentional.** Some of these will be caught by the LL-030
> triggers rather than by service code. That is the correct outcome — assert the failure
> occurs and note which layer caught it. Do not remove a database constraint because
> service validation duplicates it; defense in depth is the design.
>
> Document transaction behavior in `/docs/ACCOUNTING_RULES.md` and `/docs/DATABASE.md`.
