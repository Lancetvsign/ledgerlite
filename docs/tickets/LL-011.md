# LL-011 — Users, Companies, Memberships


**Branch** `feat/ll-011-identity-and-tenancy`
**Use plan mode.** This is one migration covering three interdependent tables.

> Implement LL-011: the LedgerLite identity and tenancy domain. Three tables, **one
> reviewed migration**.
>
> **`users`** — the application profile, separate from the Better Auth identity.
> Fields: `id` (UUID), auth identity reference, email, display name, status, created_at,
> updated_at. Never duplicate authentication secrets here. Enforce a unique constraint
> on the auth identity reference. Implement controlled provisioning when an
> authenticated user first enters the system, and document the relationship between a
> Better Auth user and a LedgerLite user in `/docs/ARCHITECTURE.md`.
>
> **`companies`** — `id` (UUID), legal name (required), DBA name, address JSON, phone,
> email, EIN placeholder held in a protected column (encryption is out of scope for
> this ticket but the column must be designed so it is never logged or returned by
> default), fiscal year start month, currency code, timezone, status, timestamps.
>
> **`company_memberships`** — `company_id`, `user_id`, role, status, timestamps.
> A user may belong to many companies; a company may have many users.
> **Unique constraint on `(company_id, user_id)`.**
>
> **Tenancy constraint — required.** Add `UNIQUE (company_id, id)` to `companies` and
> to every tenant-owned table created from now on. This unlocks composite foreign keys
> in later tickets, which make cross-company references impossible at the database
> level rather than merely discouraged. Document this pattern in `/docs/DATABASE.md` as
> a standing requirement for all future tenant-owned tables.
>
> **Atomicity requirement.** Creating a company and its creator's OWNER membership is a
> single transaction using `dbTx`. Either both exist or neither does. There must be no
> window in which a company exists with no owner.
>
> Queries: list companies for a user, list users for a company, check active membership.
> All company-scoped.
>
> **Tests:** valid company creation; missing legal name rejected; invalid fiscal month
> rejected; unsupported currency rejected; single membership; multiple companies per
> user; duplicate membership rejected by the database constraint, not just by service
> code; inactive membership excluded from active queries; and — importantly — **company
> creation rolls back completely when owner membership insertion fails.** Force that
> failure and assert no orphaned company row remains.
