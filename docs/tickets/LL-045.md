# LL-045 — Payment UI (receive, apply to open invoices, void)

**Branch** `feat/ll-045-payment-ui`

> Give customer payments a browser UI on the LL-044 pattern: list payments, receive a payment
> (pick a customer, apply amounts to that customer's open invoices, choose the deposit account),
> and void a payment. **No schema change**; one read (`listOpenInvoices`) is added to expose each
> open invoice's *open balance* for the apply screen (and as the LL-046 aging foundation).

## What was built
- **`listOpenInvoices`** (payments service) — OPEN invoices with `openBalance = total − Σ(non-void
  applications)`, one grouped query, balance computed with decimal.js (ADR-004). `invoice.view`.
- **`/payments`** — list (date / customer / reference / status / amount) with a status filter + a
  capability-gated **Receive payment** link.
- **`/payments/new`** — `payment-form.tsx`: customer picker → that customer's open invoices with open
  balances + per-invoice apply amounts (with a "Full" shortcut); deposit-account picker (active ASSET,
  excluding A/R); date/method/reference/memo; **advisory** decimal.js total → `receivePaymentAction`.
- **`/payments/[id]`** — detail (customer, amount, deposit, method/ref, status, the applications) with
  a **Void** button for a POSTED payment (`voidPaymentAction`).
- Nav link on `/account`; e2e coverage.

Company comes from the session context, never a form field; pages gate cosmetically and the LL-043
service re-authorizes (`payment.create`) and re-derives on the server.

**Test results:** lint ✓ · typecheck ✓ · **integration ✓ (payments 19)** · **e2e ✓ (all 5 setups + payments
2/2, in a production build)** · build ✓. No schema/tenancy change, so isolation/gate2/gl are unaffected
(CI re-runs the full set). The LL-044 E2E rate-limit bypass held with a fifth setup.

**Accounting implications:** none new — the UI is a thin surface over the LL-043 service, which
re-derives the amount (Σ applications) and re-validates every application on the server. Open balances
are derived, never stored (invariant 2). Money in forms is advisory; `parseFloat` is never used for money.

**Security implications:** pages gate cosmetically; `receivePayment`/`voidPayment` re-authorize
(`payment.create`) and fail closed. Company is the session's active company, never a form field; a
forged payment/invoice/customer id is scoped by companyId in the service and reads as not-found. The
deposit picker excludes A/R (the service rejects depositing there); pickers are company-scoped.

**Decisions made not specified in the ticket:** added `listOpenInvoices` (a read) to expose open
balances for the apply UX; the deposit-account list is active ASSET accounts minus A/R.

**Known limitations:** the picker can't resolve a customer/account whose display name is shared by two
records (mirrors LL-044); the new-payment page loads all company open invoices client-side; no
overpayment/credit (fully-applied only, per LL-043).

**Recommended follow-up:** LL-046 A/R aging (builds on `listOpenInvoices`); by-id lookups to avoid
loading full lists for name resolution; surfacing account/customer numbers in pickers.
