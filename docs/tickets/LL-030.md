> ### `journal_entries`
> `id` (UUID), `company_id`, `entry_number`, `transaction_date`, `posting_date`,
> `description`, `status`, `source_type`, `source_id`, `idempotency_key`,
> `reversal_of_id` (nullable), `reversed_by_id` (nullable), `created_by`, `created_at`,
> `posted_at` (nullable).
>
> Status: `DRAFT`, `POSTED`, `REVERSED`.
> `source_type` must accommodate: `INVOICE`, `CUSTOMER_PAYMENT`, `CUSTOMER_REFUND`,
> `CREDIT_MEMO`, `EXPENSE`, `DEPOSIT`, `TRANSFER`, `JOURNAL_ENTRY`, `OPENING_BALANCE`,
> `REVERSAL`.
>
> `entry_number` is allocated per **ADR-003**. Implement exactly what that ADR decided.
> Do not use `MAX(entry_number) + 1`.
>
> ### `journal_lines`
> `id`, `journal_entry_id`, `company_id`, `account_id`, `line_number`,
> `customer_id` (nullable, future), `vendor_id` (nullable, future), `description`,
> `debit NUMERIC(19,4)`, `credit NUMERIC(19,4)`, `created_at`.
>
> ### Database-level invariants — the core deliverable
>
> These are not belt-and-braces. They are the guarantees. Application code can be
> wrong; a future feature module can forget; an agent six months from now can
> misunderstand. These constraints cannot.
>
> ```sql
> -- 1. Sign discipline: exactly one of debit/credit positive, neither negative
> ALTER TABLE journal_lines ADD CONSTRAINT jl_sign CHECK (
>   debit >= 0 AND credit >= 0 AND (debit > 0) <> (credit > 0)
> );
>
> -- 2. Tenancy: a line cannot reference another company's account or entry
> ALTER TABLE journal_entries ADD CONSTRAINT je_company_id_key UNIQUE (company_id, id);
> ALTER TABLE journal_lines
>   ADD CONSTRAINT jl_account_same_company
>     FOREIGN KEY (company_id, account_id) REFERENCES accounts (company_id, id),
>   ADD CONSTRAINT jl_entry_same_company
>     FOREIGN KEY (company_id, journal_entry_id)
>       REFERENCES journal_entries (company_id, id) ON DELETE CASCADE;
>
> -- 3. Idempotency: one posting per key per company
> CREATE UNIQUE INDEX je_idempotency
>   ON journal_entries (company_id, idempotency_key)
>   WHERE idempotency_key IS NOT NULL;
>
> -- 4. One posted entry per source transaction
> CREATE UNIQUE INDEX je_source_posted_once
>   ON journal_entries (company_id, source_type, source_id)
>   WHERE status = 'POSTED' AND source_id IS NOT NULL;
>
> -- 5. Line ordering is deterministic
> ALTER TABLE journal_lines ADD CONSTRAINT jl_line_number
>   UNIQUE (journal_entry_id, line_number);
> ```
>
> **6. Debits equal credits — enforced at COMMIT.** Write a `DEFERRABLE INITIALLY
> DEFERRED` constraint trigger. Deferral is essential: lines are inserted one at a time,
> so the entry is legitimately unbalanced mid-transaction and only needs to balance when
> the transaction commits. A non-deferred trigger would reject every valid posting.
>
> The trigger must also reject a `POSTED` entry with fewer than two lines, and reject a
> `POSTED` entry with zero lines.
>
> **7. Posted entries are immutable.** A `BEFORE UPDATE OR DELETE` trigger on both
> tables that raises when the existing row's status is `POSTED`. Permit exactly one
> transition — `POSTED` → `REVERSED` with `reversed_by_id` being set — and nothing else.
> Every other column change on a posted row raises `POSTED_ENTRY_IMMUTABLE`.
> Document the permitted transition precisely in the migration and in
> `/docs/ACCOUNTING_RULES.md`.
>

> `(company_id, transaction_date)`,
> `(journal_entry_id)`,

> ### Verification — required, and report the actual output
>
> Prove each constraint by attempting the violation **in raw SQL, bypassing the
> application entirely**, and confirming the database rejects it:
> negative debit; both debit and credit positive; both zero; account from another
> company; entry from another company; duplicate idempotency key; second posted entry
> for one source; unbalanced entry at commit; single-line posted entry; update of a
> posted entry; delete of a posted line.
>
> Do not implement posting logic in this ticket. Schema, constraints, triggers, Drizzle
> types, and constraint tests only.
