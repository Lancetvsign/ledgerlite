# LL-004 — Structured Logging and Redaction


**Branch** `feat/ll-004-structured-logging`

> Implement LL-004. Create centralized server-side structured logging with levels
> debug / info / warn / error, and correlation ID support so a request can be traced
> across services.
>
> **The redaction mechanism is the point of this ticket.** Build a reusable redactor
> and apply it at the logger boundary so redaction cannot be forgotten at a call site.
> It must redact, by key name and by value shape: passwords, auth tokens, session
> cookies, `DATABASE_URL` and anything resembling a connection string, bank credentials,
> EIN/TIN values, and file contents. Handle nested objects and arrays. Handle a secret
> that appears inside an Error message or stack trace.
>
> Development gets a human-readable format; deployed environments get structured JSON
> suitable for Vercel log ingestion.
>
> **Tests:** for each protected field name, prove the value is absent from the emitted
> output. Include an adversarial case — a secret nested three levels deep inside an
> error's `cause` — and confirm it is still redacted. If your implementation cannot
> catch that case, say so explicitly rather than adjusting the test.
>
> Document logging rules in `/docs/SECURITY.md`.
