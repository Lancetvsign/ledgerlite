# LL-012 — RBAC Capability Model


**Branch** `feat/ll-012-rbac`

> Implement LL-012: capability-based authorization.
>
> Roles: `OWNER`, `ADMIN`, `BOOKKEEPER`, `ACCOUNTANT`, `READ_ONLY`.
>
> Capabilities: `company.manage`, `user.manage`, `account.view`, `account.manage`,
> `period.view`, `period.close`, `journal.view`, `journal.create`, `journal.post`,
> `invoice.view`, `invoice.create`, `invoice.post`, `payment.view`, `payment.create`,
> `expense.view`, `expense.create`, `reconciliation.view`, `reconciliation.complete`,
> `report.view`, `accountant_export.create`.
>
> Roles map to capability sets in **one** central definition. Business code asks
> "does this user have `journal.post` for this company", never "is this user an ADMIN".
> Add a lint rule or boundary check that flags role-name string comparison outside the
> permission module — hard-coded role checks scattered through business logic is the
> failure mode this ticket exists to prevent.
>
> Type the capability identifiers as a union so a typo is a compile error rather than a
> silent permission grant.
>
> **`OWNER` does not bypass membership.** An owner of Company A has no capabilities in
> Company B. Test this explicitly.
>
> **Tests:** the complete expected capability set for each of the five roles, asserted
> exhaustively so that adding a capability without deciding its role mapping fails the
> build rather than defaulting to granted or denied by accident.
