# LL-070 — Bound the Integration CI job's wall-clock (sharding investigation)

**Branch** `chore/ll-070-integration-ci-time` · **Status** Implemented (see §11) · **Origin** Gate 5
(CI operations). The Integration job's growth, tracked properly.

> The `Integration (ephemeral Neon branch)` job runs the DB-backed suite serially against one Neon
> branch. Through Sprint 4 it was ~3–16 min; Sprints 5–6 grew it to a steady ~27–30 min and it
> began **timing out a green suite** at the old 30-min cap (three consecutive PR timeouts at Gate 5).
> Gate 5 raised the cap to **45 min** as an immediate unblock (`.github/workflows/ci.yml`), but the
> suite keeps growing (each new document type adds concurrency + reconciliation tests), so 45 will
> erode too.
>
> ### Investigate (pick with data)
> - **Shard** across N parallel matrix jobs, each on its OWN ephemeral Neon branch. The original
>   comment rejected this fearing branch contention was the cause — measure whether it actually is
>   (per-file timing) before accepting/rejecting; the branch reaper already cleans up, and N isolated
>   branches remove the shared-branch serialization that forces `--no-file-parallelism`.
> - **Split** the heavy `adv*` / `gate*` / reconciliation files into a second job (coarser sharding).
> - **Profile & trim** the slowest files' redundant Neon round-trips (without deleting assertions,
>   AGENTS §7) — e.g. batch fixture creation.
>
> ### Done when
> A typical Integration run finishes with comfortable headroom under its cap and does not need a
> re-run on a normal Neon day; the "Verify migration mechanics" step reliably runs (it is currently
> the first casualty of a timeout).

## §11 — End-of-ticket report

**Ticket:** LL-070 — shard the Integration CI job across parallel Neon branches to bound wall-clock.
**Branch:** `chore/ll-070-integration-ci-time`

**Approach chosen (of the three investigated):** **Shard** across a matrix of N parallel jobs, each on
its OWN ephemeral Neon branch — with N=2 to start (conservative: one extra concurrent branch). The
original comment rejected splitting on a *shared-branch contention* theory; giving each shard its own
branch removes that objection entirely, and `vitest --shard=i/N` splits the files so each shard still
runs its slice serially (`fileParallelism: false` stays correct — see the refreshed note in
`vitest.config.mts`). Profiling/trimming individual tests' round-trips is deliberately left as a
separate, deeper follow-up (see Recommended follow-up).

**The required-check-name problem & fix:** branch protection requires a check literally named
`Integration (ephemeral Neon branch)`. A matrix job reports one status *per shard*
(`Integration shard 1/2`), which would make the required check vanish and block every PR until a
*settings* change (not code). So the matrix job is renamed `integration-shards`, and a tiny
**aggregator job named exactly `Integration (ephemeral Neon branch)`** (`needs: [integration-shards]`,
`if: always()`) becomes the required check — it fails unless `needs.integration-shards.result ==
'success'`. The guard is `== 'success'` (not `!= 'failure'`) on purpose, so a `cancelled`/`skipped`
shard also reds the check: an unrun integration suite must never read as a pass (the same principle the
credential-guard step enforces).

**Files changed:**
- `.github/workflows/ci.yml` — renamed `integration` → `integration-shards` with
  `strategy: { fail-fast: false, matrix: { shard: [1, 2] } }`, `name: Integration shard ${{ matrix.shard }}`,
  a per-shard `BRANCH_NAME` (…`-shard-${{ matrix.shard }}`), test step
  `npm run test:integration -- --shard=${{ matrix.shard }}/2`, and `db:verify` gated to shard 1 only
  (whole-history replay, identical per branch). Added the `integration` aggregator job. Refreshed the
  block comment (was "splitting stays rejected"). Kept the Neon-credential guard, fork `if:` guard, and
  per-shard `always()` branch cleanup.
- `vitest.config.mts` — refreshed the `fileParallelism`/timeout comments to describe the shard model
  (no behavior change; `fileParallelism: false` and the 90 s timeouts stay).
- `docs/tickets/LL-070.md` — this report.

**Migrations created:** none.
**DB constraints added:** none.
**Tests added:** none — this is CI-topology only, no application behavior. The proof is the PR's own CI
(see below); no unit/integration test can assert GitHub Actions job wiring.
**Test results:** `npm run ci` (lint / typecheck / unit / build) unaffected — no app code changed.
E2E / integration unchanged in content. The sharding itself is verified by **this PR's own CI**: two
`Integration shard n` jobs run in parallel (each ~half the old wall-clock), `db:verify` runs once on
shard 1, and the `Integration (ephemeral Neon branch)` aggregator reports the combined result and gates
the merge.

**Accounting implications:** none — no ledger, schema, or posting path touched. The change only bounds
how long the existing invariant checks take to run; it does not weaken any of them (all shards must be
green; a skipped/cancelled shard reds the required check).
**Security implications:** none new. Each shard re-runs the same credential guard and masks its own
connection strings; the fork guard is preserved so forks (no secrets) still cannot run it.
**Decisions made not specified in the ticket:** (1) N=2 to start rather than 3 — conservative on Neon
concurrent-compute; N is a one-line matrix edit to raise once capacity is confirmed. (2) Added a name-
preserving aggregator rather than asking for a branch-protection settings change, so no required-check
reconfiguration is needed.
**Known limitations:** a run now creates 2 integration branches instead of 1 (≈4 concurrent ephemeral
branches at peak with GL-regression + E2E); the reaper + per-shard `always()` cleanup bound leakage.
CI *minutes* rise ~N× for setup (npm ci + branch create + migrate), traded for ~N× faster wall-clock,
which is what blocks merges.
**Recommended follow-up:** (a) once a few runs confirm timings, consider N=3 if a shard still runs hot;
(b) a separate ticket to profile and trim the slowest files' redundant Neon round-trips (batch fixture
creation) — the deeper optimization, out of scope here.
