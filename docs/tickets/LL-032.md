# LL-032 — Idempotency and Concurrency


**Branch** `feat/ll-032-ledger-idempotency`

> Implement LL-032: idempotent posting, proven under real concurrency.
>
> The scenario that matters: a caller posts, the network times out, the caller retries
> the identical request. The result must be **one** journal entry, and the retry must
> receive a successful response identifying the existing posting — not an error, and
> certainly not a second entry.
>
> Behavior:
> - **Identical retry** → returns the existing posting. Success, not an error.
> - **Same key, materially different payload** → fails with
>   `IDEMPOTENCY_KEY_CONFLICT`. Never silently returns the original, which would hide a
>   caller bug and lose a transaction.
> - **Same key across different companies** → independent; keys are scoped per company.
> - **Missing key on a posting that requires one** → rejected.
>
> **Implement on the database's unique index, not on check-then-insert.** A read
> followed by a conditional write has a race window between them; two concurrent
> requests both read "not found" and both insert. Attempt the insert, catch the unique
> violation, and resolve on conflict. Store enough of a payload fingerprint to
> distinguish an identical retry from a conflicting one.
>
> ### Concurrency tests — real database, real parallelism
>
> Mocked concurrency proves nothing here. Use actual concurrent connections.
>
> - Two simultaneous requests, same idempotency key → exactly one entry
> - Five simultaneous requests, same key → exactly one entry
> - Delayed race: request A begins its transaction, request B completes fully, A then
>   attempts to commit
> - Same key with conflicting payloads, submitted concurrently
> - Distinct legitimate keys concurrently → both post, both balance
> - Concurrent postings to the same account → both succeed, both correct
> - Concurrent `entry_number` allocation → no duplicates, and behavior matches ADR-003
>
> After **every** concurrency test assert three things: every posted entry balances;
> each source transaction posted exactly once; no partial journal exists — no entry
> without lines, no line without an entry.
>
> Document the concurrency strategy in `/docs/ACCOUNTING_RULES.md`: which unique
> constraints carry the guarantee, what isolation level applies, how conflicts surface,
> and what a caller should do on each error code.
