# LL-021 — Append-Only Audit Events


**Branch** `feat/ll-021-audit-events`

> Implement LL-021: append-only audit infrastructure. Build it now because period
> close, journal posting, and reversal all depend on it.
>
> Table `audit_events`: `id`, `company_id`, `actor_user_id`, `action`, `entity_type`,
> `entity_id`, `before_json`, `after_json`, correlation/request metadata, `created_at`.
>
> **Append-only means enforced, not intended.** Add a database trigger that raises on
> `UPDATE` or `DELETE` against this table. Application-level discipline is not
> sufficient for an audit log — the whole value of the record is that it cannot be
> revised after the fact. Test by attempting an `UPDATE` in raw SQL and confirming the
> database refuses.
>
> Apply the standard tenancy constraints: `UNIQUE (company_id, id)` and a composite
> foreign key to `companies`.
>
> Pass `before_json` and `after_json` through the LL-004 redactor before writing. An
> audit log full of secrets is a liability, and the entity being audited will eventually
> contain sensitive fields. Test that a known secret field name never lands in
> `before_json`.
>
> Design the write API so a future financial action can emit an audit event **inside
> the same transaction** as the action it records. An audit event written in a separate
> transaction can survive a rolled-back posting, which produces a log entry for
> something that never happened. Make the transactional path the default and document
> why.
>
> Seed the action vocabulary as a typed union. Register `audit_events` in the isolation
> harness.
