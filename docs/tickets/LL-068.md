# LL-068 — Accounts Payable in the required (system-only) chart

**Branch** `feat/ll-068-ap-required-account` · **Status** Implemented (see §11) · **Origin** Gate 5
(correctness finding 7). LOW / functional-gap, fails closed.

> `REQUIRED_SYSTEM_ACCOUNTS` (`src/server/accounts/default-coa.ts`) lists A/R but **not A/P**, so a
> company created on the `'system-only'` chart has no Accounts Payable control account. Every A/P
> document then fails with `AP_ACCOUNT_NOT_CONFIGURED` until `installDefaultChartFor('standard')`
> runs. The `'standard'` chart is fine (it seeds 2000 Accounts Payable, tagged by migration 0022);
> only the minimal chart is short.
>
> ### Approach
> Add `ACCOUNTS_PAYABLE` to `REQUIRED_SYSTEM_ACCOUNTS` so every company — minimal or standard — has
> an A/P control from creation, mirroring A/R. Decide (ADR note) whether existing `'system-only'`
> companies get a backfill migration (like 0022 did for A/P numbering) or A/P is created lazily on
> first use. Fails closed today, so this is correctness-of-completeness, not a live corruption.
>
> ### Tests
> A `'system-only'` company can raise and pay a bill end to end without manually creating A/P;
> `default-coa` unit test asserts A/P is in the required set.

## §11 — End-of-ticket report

**Ticket:** LL-068 — Accounts Payable in the required (system-only) chart.
**Branch:** `feat/ll-068-ap-required-account`

**Files changed:**
- `src/server/accounts/default-coa.ts` — added `2000 Accounts Payable` (`ACCOUNTS_PAYABLE`) to
  `REQUIRED_SYSTEM_ACCOUNTS` (after A/R); removed the now-duplicate explicit line from `STANDARD_CHART`
  (which spreads the required set), so A/P appears exactly once and the standard chart's content is
  unchanged. No installer change — `installDefaultChart` already inserts `chartFor(choice)` idempotently.
- `drizzle/migrations/0026_backfill_ap_system_account.sql` — new custom **DML-only** migration.
- `docs/DECISIONS.md` — ADR-027.
- `tests/integration/default-coa.test.ts` — required-set assertion now four accounts, A/P after A/R.
- `tests/integration/bill-payments.test.ts` — `setupSystemOnly` fixture + end-to-end acceptance test.
- `docs/tickets/LL-068.md` — this report.

**Migrations created:** `0026_backfill_ap_system_account.sql` — inserts a `2000 Accounts Payable`
(`ACCOUNTS_PAYABLE`) row for every company that has no `ACCOUNTS_PAYABLE` system account, skipping any
company already using number `2000` for a different account. Idempotent (NOT EXISTS guards +
`ON CONFLICT DO NOTHING`); no DDL, so the Drizzle snapshot / `db:check` is unaffected. Backfills
pre-LL-068 `'system-only'` companies without lazy logic on the posting paths.

**DB constraints added:** none.
**Tests added:**
- `default-coa.test.ts` "names the four required system accounts, A/P alongside A/R" — proves A/P is in
  the required set in the expected position; the existing `'system-only'` length/flagged-as-system tests
  now cover A/P automatically (they reference `REQUIRED_SYSTEM_ACCOUNTS`).
- `bill-payments.test.ts` "raises and pays a bill end to end without a manually-created A/P account" —
  the ticket's acceptance test: on a `'system-only'` company, A/P resolves from creation, `finalizeBill`
  (which posts Cr A/P — the pre-fix `AP_ACCOUNT_NOT_CONFIGURED` throw site) succeeds, the payment clears
  the bill to PAID, the A/P control returns to zero, and `assertLedgerIntegrity` passes.

**Test results:** lint ✓ / typecheck ✓ / unit ✓ / build ✓ (local `npm run ci`). Integration + e2e +
GL-regression run on the PR's CI (integration is DB-backed and, per the contract, not run locally
against the shared dev branch); the new integration test and the migration replay are proven there.

**Accounting implications:** the minimal chart can now transact payables from creation, symmetric with
receivables. No posting logic or invariant changed — only the presence of a control account that the
posting path already knew how to resolve. Backfill inserts a control account only; it creates no
journal entries and no balances.

**Security implications:** none. The backfill is scoped per company via the correlated subqueries;
`resolveSystemAccount` continues to resolve by `(company_id, system_account_type)`. No auth path touched.

**Decisions made not specified in the ticket:** chose the **backfill migration** over lazy
create-on-first-use (product owner confirmed) — keeps write logic off the financial posting paths and
fixes existing data once; recorded as ADR-027 with the number-2000-taken edge case.

**Known limitations:** a `'system-only'` company that had manually created a non-A/P account numbered
`2000` is skipped by both the backfill and the installer (both place A/P at `2000` and both use
`ON CONFLICT DO NOTHING`, so neither can seat it while `2000` is occupied). Such a company must free
number `2000` (or create A/P manually) to gain the control account. Rare; called out in ADR-027.

**Recommended follow-up:** none specific; LL-069 (audit-field allow-list) remains the last Gate 5
follow-up.
