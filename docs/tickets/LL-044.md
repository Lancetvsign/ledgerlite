# LL-044 — Invoice UI (+ minimal customers page)

**Branch** `feat/ll-044-invoice-ui`

> Give the invoice lifecycle a browser UI: browse invoices, create/edit a DRAFT, finalize it
> (posts to the GL), and void it — plus a minimal customers page, since an invoice needs a
> customer and there was no customer UI. Mirrors the LL-024 `/accounts` + LL-035 `/journal`
> server-component + server-action pattern. **No schema change, no new service.**

## What was built
- **`/customers`** — list + a create form (server action `createCustomerAction` → `createCustomer`).
- **`/invoices`** — list with a status filter and a capability-gated New-invoice link.
- **`/invoices/new`** + **`/invoices/[id]/edit`** — a shared client `InvoiceForm` (customer + account
  datalist pickers resolving to hidden ids, line items, decimal.js **advisory** totals) posting
  `createInvoiceAction` / `updateInvoiceAction`.
- **`/invoices/[id]`** — detail with the lifecycle action the status allows: DRAFT → Edit + Finalize,
  OPEN → Void (server actions `finalizeInvoiceAction` / `voidInvoiceAction`). PAID/VOID read-only.
- Nav links on `/account`; e2e coverage.

Every page resolves the company from the **server session context** (never a form field) and
capability-gates cosmetically; the LL-041/042 services re-authorize and re-derive on the server.

**Accounting implications:** none new — the UI is a thin surface over the LL-041/042 services, which
remain the sole authority (they re-derive totals with decimal.js and re-authorize). Money in forms is
advisory only; `parseFloat` is never used for money (ADR-004).

**Security implications:** pages gate on capabilities cosmetically; `create/update/finalize/void`
actions re-authorize on the server and fail closed. The company is the session's active company,
never a form field; a forged invoice/customer id is scoped by companyId in the service and reads as
not-found. Pickers are built from company-scoped, active records, so they cannot surface another
tenant's or a deactivated record (proven in the e2e).

**Decisions made not specified in the ticket:** LL-044 had no written spec; scope was set this session
to **invoices UI + a minimal customers page** so an invoice can be created and settled end-to-end.

**Known limitations:** the picker can't resolve a customer/account whose display name is shared by two
records (mirrors the journal picker); the line picker offers REVENUE accounts only; no payment UI yet
(LL-045); a PAID invoice is read-only here (void its payment in LL-045).

**Recommended follow-up:** LL-045 payment UI (receive/apply/void); LL-046 A/R aging; showing the
posted journal entry on the invoice detail; a fuller customer management page.
