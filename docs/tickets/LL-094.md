## §11 — End-of-ticket report

**Ticket:** LL-094 — detect the mirror of a transfer across two imported statements and post it once.
**Files changed:** `src/server/bank-import/index.ts` (`findTransferCandidates`, `transferCandidate` on the
review view, `match_transfer` plan + execution, `TRANSFER_ALREADY_POSTED` guard on `post`, `matched` in the
result), `errors.ts`, `extract.ts` (the canned extractor returns a card statement for card imports),
`src/validation/bank-import.ts` (`match_transfer`, `counterpartLineId`);
`src/app/bank-import/[batchId]/{page,line-action,review-state}.tsx` and `actions.ts` (transfer flag,
Match option, counterpart field, default action, notices); ADR-034 amendment; `docs/GATE-6.md` (M1 fixed);
this ticket.
**Migrations created:** none — the matched line reuses `status = POSTED` + `journal_entry_id` pointing at
the counterpart's entry. **DB constraints added:** none (one-mirror-per-entry is checked under the
counterpart's row lock; a partial unique on `(journal_entry_id) WHERE …` would need a schema change and is
noted for the housekeeping ticket).
**Tests added:** `tests/integration/bank-import.test.ts` — posted bank side flags the card payment as its
mirror; matching marks it POSTED against the same entry, creates no entry, and the card/bank balances are
right; posting the exact mirror is `TRANSFER_ALREADY_POSTED`; wrong / missing / staged counterpart is
`TRANSFER_MISMATCH`; a second statement cannot match the same entry again; both-sides-staged is flagged but
not matchable. `tests/e2e/bank-import.spec.ts` — bank statement posts the card payment to the card; the card
statement shows the flag, defaults to Match, posts 2 + matches 1; trial balance shows one movement
(Checking −620.50, Card −1,834.50) and the dashboard lists 5 entries, not 6. The LL-088 card e2e updated to
the card-specific canned rows.
**Test results:** lint ✓ / typecheck ✓ / unit ✓ / build ✓ (`npm run ci`); bank-import e2e ✓ locally;
integration on CI.
**Accounting implications:** a two-sided source posts exactly once (invariant 6 in spirit); every other
posting path is unchanged; a matched line carries the real entry id, so reconciliation pre-ticks it.
**Security implications:** none; all lookups company-scoped; the counterpart is re-locked and re-verified
inside the transaction.
**Decisions made not specified in the ticket:** a three-day window and exact opposite amount define a
candidate; matching requires the other side to be POSTED (both-staged is flagged only); the exact-mirror
`post` is refused rather than confirmed.
**Known limitations:** one candidate per line (the best by status then date); no structural unique on the
mirror; checking↔savings transfers are handled identically but not separately tested.
**Recommended follow-up:** partial unique index for the mirror in the housekeeping ticket.
