# LL-053 — Void authorization & idempotent writes


**Branch** `feat/ll-053-void-authz-idempotency`

**Status** Backlog · **Origin** Sprint 5 plan · closes [GATE-3.md](../GATE-3.md) §7 items 4–6
and [GATE-2.md](../GATE-2.md) §7 item 9. See [SPRINT-5-PLAN.md](../SPRINT-5-PLAN.md).

> Two loose ends around *undoing* and *retrying* financial writes. Mostly app-layer; a small
> migration only if the idempotency key needs a column.
>
> ### Distinct void capability
> Today `voidInvoice` requires `invoice.post` and `voidPayment` requires `payment.create`,
> both `ALL_WRITERS` — so any writer who can post can also void (Gate 3 item 4). Add
> **`invoice.void` / `payment.void`** capabilities, granted to **MANAGERS** (a reversal of a
> posted entry is a heavier action than creating one). Capability-based, fail-closed,
> enforced in both the pre-check and the locked transaction — no role-name comparisons.
>
> ### Idempotent writes (submit-once)
> - `receivePayment` has no idempotency key: a double-submitted **partial** payment creates
>   two payments (Gate 3 item 5). Wire a **submit-once / per-form idempotency key** so a
>   double-submit resolves to one payment (the ledger already has the source-once index; this
>   extends it to the document).
> - The **manual journal entry** path has the same double-submit exposure (Gate 2 item 9).
>   Give it a per-form idempotency key too.
>
> ### Explicit lock
> `voidPayment` reverts PAID→OPEN via `where status='PAID'` without an explicit `FOR UPDATE`
> on the invoice rows — verified safe today via the implicit UPDATE lock, but take the lock
> explicitly for clarity and future-proofing (Gate 3 item 6).
>
> ### Tests
> A BOOKKEEPER can post an invoice/payment but **cannot void** either (denied), while a
> MANAGER can; a double-submitted partial payment (and manual JE) yields **one** entry, not
> two; the explicit `voidPayment` lock serializes correctly against a concurrent
> `receivePayment` on the same invoice.
>
> ### Not in scope
> New document types; the trigger/redaction hardening (that is LL-052).

**Tests added:** `void-authorization.test.ts` (4) — for each document type, a BOOKKEEPER can
create/post but is denied the void (`AuthorizationDenied`), and an ACCOUNTANT can void. Existing void
tests (payments/writeoffs/credit-memos/invoice-posting) still pass (they void as OWNER) and cover the
FOR-UPDATE change's behavior.

**Test results:** lint ✓ · typecheck ✓ · unit ✓ (175, rbac matrix updated) · integration ✓
(void-authz 4 + the void suites 49 together; full suite as the gate) · build ✓.

**Accounting implications:** none to the ledger math; void (a reversal) is now a LEDGER_WRITERS
correction, consistent with manual reversals.

**Security implications:** tighter authorization — a BOOKKEEPER can no longer undo posted documents;
the void↔create race on an invoice's status is now serialized by an explicit lock.

**Decisions made not specified in the ticket:** ADR-021 — LEDGER_WRITERS grant (not MANAGERS);
idempotency + shared-core refactor deferred.

**Known limitations:** submit-once idempotency not yet implemented (double-submit can still create two
payments / two manual entries — a distinct source each, not an invariant violation); void buttons are
still shown to non-void roles in the UI (the service denies; hiding them is a later nicety).

**Recommended follow-up:** the idempotency ticket (payment idempotency key + form tokens) and the
writeoffs/credit-memos shared-core extraction; then LL-054/055 (statements + reporting UI) and Gate 4.
