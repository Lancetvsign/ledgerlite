# LL-046 — A/R aging report + regression (closes Sprint 4)

**Branch** `feat/ll-046-ar-aging`

> The A/R aging report — open receivables bucketed by age, per customer — plus the invariant that
> makes it trustworthy: the aging grand total equals the general-ledger Accounts Receivable control
> balance, enforced by the release gate. A service report (like `getTrialBalance`), **no schema
> change, no UI.** See **ADR-016**.

## What was built
- **`getArAging(actorUserId, companyId, asOfDate)`** (`src/server/reports/ar-aging.ts`) — every OPEN
  invoice's open balance (`total − Σ non-void applications`, one SQL aggregation), grouped by customer,
  bucketed **Current / 1–30 / 31–60 / 61–90 / 90+** by `due_date` (fallback `invoice_date`). Mirrors
  `trial-balance.ts`: `report.view`, `isCalendarDate`, `getDb()` HTTP client, decimal.js money.
- **GL-T018** (release gate) — the subsidiary⇔control reconciliation: aging grand total equals the
  derived A/R balance, and still equals it after a payment void.

**Accounting implications:** A/R now has a customer-facing aging that provably ties to the books — the
subsidiary⇔control reconciliation is a merge-blocking invariant (ADR-016). No balance is stored; the
aging derives from invoices + applications every time (invariant 2).

**Security implications:** `getArAging` authorizes `report.view` and fails closed; it is company-scoped
(a query filtered by companyId, joined only to this company's customers), so another tenant's
receivables never appear (proven in the tests). Money is a string throughout; PostgreSQL does the
aggregation and decimal.js the bucket sums (ADR-004).

**Decisions made not specified in the ticket:** ADR-016 — the bucket definitions, aging by due date
(fallback invoice date), that "as of" ages the current balances (not point-in-time historical), and
the reconciliation as a release-gate invariant.

**Known limitations:** aging is of *current* open balances (no point-in-time historical aging); no
aging UI (reports are service-level, like the trial balance); buckets are fixed (not configurable).
The subsidiary⇔control reconciliation **assumes A/R is posted only via invoices/payments** — a manual
journal entry to A/R would break it and nothing currently prevents that (ADR-016).

**Recommended follow-up:** lock the A/R (and other system) control accounts from manual journal
entry, so the reconciliation is structurally enforced, not just assumed; a reports UI surfacing the
trial balance + aging; point-in-time historical aging if needed; customer statements built on the
same data. **Sprint 4 (A/R) is complete — Gate 3.**
