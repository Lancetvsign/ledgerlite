# LL-050 — Control accounts are protected from ad-hoc manual entry


**Branch** `feat/ll-050-control-account-protection`

**Status** Backlog · **Origin** Gate 3 follow-up (accepted by the product owner) · see
**ADR-016** and [GATE-3.md](../GATE-3.md) §7 item 2.

> Close the last path that can break the A/R aging⇔control reconciliation. The aging
> (subsidiary) ties to the general-ledger A/R (control) **only because A/R is moved solely
> by invoices and payments** — GL-T018 proves the tie for that document-driven data. The
> **manual journal-entry path (LL-035) can still post to any account, including A/R**, so a
> hand-posted entry to the control account would make the control diverge from the aging
> with nothing detecting it. Gate 3 already closed the sibling path (an invoice line naming
> a control account is now rejected, `LINE_ACCOUNT_INVALID`); this ticket closes the manual
> path.
>
> ### Why this is not a one-line lock
> A blanket "no manual entry may touch A/R" is **wrong** — some manual A/R movements are
> legitimate and expected:
> - **Bad-debt write-off** — `Dr Bad Debt Expense / Cr A/R`.
> - **Opening balances** at migration onto the system — `Dr A/R / Cr Opening Balance Equity`.
>
> These must remain possible; the problem is only *ad-hoc, untracked* control-account
> entries that the subsidiary does not know about. So this is a **design decision, needing
> an ADR**, not a mechanical guard.
>
> ### Approach to evaluate (pick in the ADR)
> 1. **Sanctioned documents + default block.** Reject manual JE lines to any system control
>    account (non-null `system_account_type`) by default, and provide first-class,
>    customer-tagged document types that post through `LedgerService` and are visible to the
>    A/R subsidiary — a **bad-debt write-off** document (and, if needed, an
>    **opening-balance** import). This keeps the subsidiary⇔control tie structural because
>    every A/R movement is document-driven and countable in the aging. *Preferred.*
> 2. **Narrower capability.** Gate manual control-account entries behind a dedicated
>    capability (e.g. `ledger.post_control`). Simpler, but it does **not** restore the
>    reconciliation — an authorized manual A/R entry still breaks GL-T018 unless the
>    subsidiary is extended to include it. Weaker; document why if chosen.
> 3. **Extend the subsidiary.** Make the aging reconcile including manual A/R adjustments
>    (customer-tagged manual lines counted as subsidiary activity). Broadest change; only if
>    the product wants free-form A/R adjustments.
>
> ### Enforcement must be structural where possible
> Whatever the policy, the default block on ad-hoc control-account entry should hold **with
> the application bypassed** (a `BEFORE INSERT` trigger on `journal_lines` that rejects a
> line to a system control account unless it carries the sanctioned source type), mirroring
> the closed-period trigger (ADR-012). Sanctioned documents post with their own source type,
> which the trigger allows.
>
> ### Tests
> - A manual JE (via the LL-035 path) to the A/R control account is **rejected** — through
>   the service **and** in raw SQL (the trigger), with the service bypassed.
> - A sanctioned bad-debt write-off posts `Dr Bad Debt Expense / Cr A/R` (customer-tagged),
>   reduces that customer's open balance, and the aging⇔control reconciliation **still
>   holds** (extend GL-T018 to include the write-off path).
> - Opening-balance entries to A/R (if in scope) reconcile the same way.
> - Legitimate manual entries to **non-control** accounts are unaffected.
>
> ### Not in scope
> Customer credits / unapplied cash and multi-currency (each changes what "the A/R balance"
> means — see ADR-016 "Revisit if").

## §11 report — PR 1 (bad-debt write-off document)

**Ticket:** LL-050 (PR 1 of 2) — the sanctioned bad-debt write-off. **PR 2** (the structural
control-account trigger) follows separately.
**Branch:** `feat/ll-050-bad-debt-writeoff`

**Files changed:**
- Schema: `src/db/schema/writeoffs.ts` (new), enum additions in `ledger.ts` (`BAD_DEBT_WRITEOFF`)
  and `audit.ts` (`WRITEOFF_POSTED/VOIDED`), `schema/index.ts` export.
- Service: `src/server/writeoffs/{index,errors}.ts` (new); `src/validation/writeoff.ts` (new).
- Shared derivation: `src/server/reports/open-balance.ts` (new) — the single open-balance
  definition; `ar-aging.ts` and `payments.ts` (`listOpenInvoices`, over-application guard)
  refactored onto it. Capability: `writeoff.view` / `writeoff.create` in `rbac/capabilities.ts`.
- Tests: `tests/integration/writeoffs.test.ts` (new); GL-T019 in `gl-regression.test.ts`;
  write-off checkpoints in `gate3-acceptance.test.ts` and `ar-aging.test.ts`.

**Migrations created:** `0017_writeoffs.sql` — creates the `writeoff_status` enum, adds the
`BAD_DEBT_WRITEOFF` source type and `WRITEOFF_POSTED/VOIDED` audit actions, and creates the
`writeoffs` table (composite FKs to invoice/customer/expense-account, `amount > 0` check,
`UNIQUE(company_id,id)`, three indexes). Additive (expand) — no drops, no data transforms.

**DB constraints added:** the three same-company composite FKs, the positivity CHECK, and the
standing tenancy UNIQUE listed above.

**Tests added:** `writeoffs.test.ts` (14 — posting, customer-tagged A/R, partial/full, PAID-on-clear,
guards for non-EXPENSE/A/R/over-balance/closed-period/not-open, tenancy, void-reverses-and-reopens);
**GL-T019** (release gate — write-off reconciles subsidiary⇔control, and after void).

**Test results:** lint ✓ · typecheck ✓ · unit ✓ · integration ✓ (writeoffs 14, gl 19; full suite as
the gate) · build (run before PR). e2e n/a (no UI in this PR).

**Accounting implications:** A/R can now be reduced for bad debt through a document the subsidiary
sees — `Dr Bad Debt Expense / Cr A/R` (customer-tagged), reducing the invoice's open balance so the
aging⇔control reconciliation (GL-T018/T019) holds. Void is by reversal (invariant 3). No balance is
stored (invariant 2).

**Security implications:** company-scoped and authorized (`writeoff.create`/`writeoff.view`, fail
closed); expense account validated in-company/ACTIVE/EXPENSE; A/R line customer-tagged via the
structural composite FK; posts only through `postEntryCore` (invariant 8). Cross-company ids read as
genuine misses.

**Decisions made not specified in the ticket:** ADR-017 — write-off is per-invoice and reduces the
open balance (the shared derivation), the expense account is user-supplied (Option A), and a full
write-off marks the invoice PAID.

**Known limitations:** a fully written-off invoice reads as PAID (a distinct `WRITTEN_OFF` status is
a possible later reporting refinement). The manual-JE-to-A/R path is **still open** — it is closed by
**PR 2** (the trigger).

**Recommended follow-up:** LL-050 PR 2 (the structural control-account trigger); then LL-051
(credits/refunds) extends the same shared open-balance derivation.

## §11 report — PR 2 (structural control-account lock) · LL-050 COMPLETE

**Ticket:** LL-050 (PR 2 of 2) — locks the manual path out of A/R. With this, **LL-050 is complete.**
**Branch:** `feat/ll-050-control-account-lock`

**Files changed:**
- Migration `0018_control_account_guard.sql` (new, hand-written trigger; `_journal.json` + `0018_snapshot.json`).
- `src/server/ledger/errors.ts` (`CONTROL_ACCOUNT_MANUAL_POST` code) + `internal.ts` (`toLedgerDomainError` branch).

- `docs/DECISIONS.md` (ADR-018; ADR-016 "Assumption" bullet → CLOSED).
- `tests/integration/control-account-guard.test.ts` (new).

**Migrations created:** `0018_control_account_guard.sql` — a `BEFORE INSERT` trigger on `journal_lines`
(`assert_no_manual_post_to_ar`) that rejects a line to the A/R control account when the parent
entry's `source_type = 'JOURNAL_ENTRY'`. No table/column/data change.

**DB constraints added:** the trigger above (structural guard; SQLSTATE `restrict_violation`).

**Tests added:** `control-account-guard.test.ts` (6) — raw-SQL manual line to A/R rejected (service
bypassed); raw INVOICE-source line to A/R allowed; service manual JE to A/R → typed
`CONTROL_ACCOUNT_MANUAL_POST`; manual JE to Sales Tax Payable and to ordinary accounts still post
(A/R-only scope); every document path (invoice/payment/write-off) still reaches A/R.

**Test results:** lint ✓ · typecheck ✓ · unit ✓ · integration ✓ (guard 6; full suite as the gate) ·
build ✓. e2e n/a.

**Accounting implications:** the aging⇔control reconciliation (GL-T018) is now **structural**, not
assumed — A/R moves only through documents the subsidiary sees. Manual A/R adjustments must go
through a document.

**Security implications:** a structural DB guard that holds with the application bypassed (proven by
raw-SQL test). Scoped to A/R only; other system accounts remain manually postable by design.

**Decisions made not specified in the ticket:** ADR-018 — A/R-only scope (not all system accounts),
and the `JOURNAL_ENTRY`-source predicate (no allow-list coupling to document types).

**Known limitations:** opening A/R balances would need a future `OPENING_BALANCE` document (raw
manual A/R posts are now blocked). `voidWriteoff`/`voidPayment` still rely on the implicit lock
(LL-053).

**Recommended follow-up:** LL-051 (credits/refunds) — extend the shared open-balance derivation and,
being a new document source, it is auto-allowed to touch A/R (no trigger change).
