# LL-000 — Architecture Decisions Spike


**Branch** `docs/ll-000-architecture-decisions`
**Produces no application code.** This is deliberate and is the most valuable ticket
in Sprint 0.

> Implement LL-000. You are producing `/docs/DECISIONS.md` for the LedgerLite
> double-entry accounting application. No application code, no schema, no dependencies
> beyond what is needed to verify a claim.
>
> For each decision below: research the actual current behavior of the named library or
> platform, verify it rather than recalling it, then write an ADR with **Context /
> Decision / Consequences / Revisit-if**. Where a decision has a real trade-off, state
> the rejected option and why it lost.
>
> **ADR-001 — Neon driver strategy.** Determine empirically whether
> `drizzle-orm/neon-http` supports interactive callback transactions
> (`db.transaction(async tx => ...)`). Write a minimal script that attempts one and
> record what actually happens. Then decide the driver split for LedgerLite and how it
> will be enforced so a financial write path cannot accidentally use the wrong client.
>
> **ADR-002 — Accounting period resolution.** A journal entry has both
> `transaction_date` and `posting_date`. Decide which one determines the accounting
> period, and therefore which one the closed-period check evaluates. Explain the
> accounting reasoning, not just the implementation convenience. Define behavior when
> the two dates fall in different periods.
>
> **ADR-003 — `entry_number` generation.** Decide how journal entry numbers are
> allocated per company. Explicitly address: are gaps acceptable? What happens when two
> requests post concurrently? Naive `MAX(entry_number) + 1` is not acceptable — explain
> why in the ADR. If you choose gapless numbering, specify the serialization mechanism
> and its throughput cost.
>
> **ADR-004 — Monetary representation.** Define the exact contract for money crossing
> every boundary: database, Drizzle, Zod schemas, service inputs, service outputs, JSON
> API, React props, test fixtures. Confirm what type Drizzle actually returns for
> `numeric` columns and record it. Specify the global decimal.js configuration
> including rounding mode, and justify the rounding mode choice for accounting.
>
> **ADR-005 — Dates and timezones.** Decide the storage type for `transaction_date`,
> how "today" is determined for a company, and how fiscal year boundaries are computed.
> State the rule that prevents server-local time from leaking into posting logic.
>
> **ADR-006 — Deletion policy.** Accounting records are never destroyed. Decide the
> single vocabulary for making a record unusable (`active` flag vs `deleted_at` vs
> status enum) and apply it consistently across accounts, companies, memberships, and
> future entities.
>
> **ADR-007 — Reversal date policy.** When a posted entry is reversed, what date does
> the reversing entry carry? Cover the case where the original entry's period is now
> closed. State what is permitted and what is refused.
>
> **ADR-008 — Row-level security.** Decide whether PostgreSQL RLS is used. A reasoned
> "no" is an acceptable outcome; an unconsidered absence is not. If no, state what
> mechanisms cover the threat model instead and what would change your mind.
>
> Also create `/docs/PR_TEMPLATE.md` and `/docs/tickets/` containing one file per
> LL ticket, seeded from the ticket plan.
>
> **Acceptance:** every ADR names a specific decision, not a menu of options. Anywhere
> you could not determine the answer with confidence, say so explicitly and flag it for
> human decision rather than guessing.

**Review this yourself before proceeding.** These eight decisions are load-bearing for
everything in Sprints 1–3.
